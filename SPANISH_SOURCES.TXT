
Spanish Offline Knowledge Strategy for offline-survival
Executive summary
The current offline-survival repository is already organized around five manifest-driven profiles — survival-essential, survival-plus, civilization-core, civilization-rebuild, and civilization-max — with target size bands that range from roughly 12–15 GB for the smallest profile to 180–260 GB for the largest. Its source catalog is declarative: each resource has an id, type, category, license, url, expected_size_bytes, and profile-group membership, while profiles compose those groups into installable packs. That architecture is a very good fit for adding parallel Spanish manifests or a --lang {en,es,both} resolver layer. 

The strongest Spanish-language substitutions are the direct Kiwix Spanish editions: Spanish Wikipedia subsets and full dumps, Wikibooks, Wiktionary, Wikivoyage, Wikisource, iFixit, and even Vikidia as the best “simple encyclopedia” replacement for simplewiki. These are the cleanest equivalents because they preserve the repo’s existing offline-reading workflow, licensing posture, and searchable ZIM format. In contrast, the weakest areas in Spanish are WikEM-like point-of-care emergency references, Stack Exchange-style practical Q&A, and OpenStax/LibreTexts-style STEM textbook bundles. For those, the best Spanish answer is usually official PDF packs from WHO/OPS, Red Cross, Protección Civil, FAO, and selected Spanish-language wiki snapshots — or a bilingual manifest that keeps the English source as an explicit fallback. 

For a practical Spanish-first build that still fits comfortably under the user’s earlier 50 GB constraint, the best balance is a core-50-es pack centered on wikipedia_es_top_nopic, wikipedia_es_medicine_nopic, ifixit_es_all, wiktionary_es_all_nopic, wikibooks_es_all_nopic, wikivoyage_es_all_nopic, wikisource_es_all_nopic, vikidia_es_all_nopic, and a compact PDF layer from WHO, Cruz Roja, Protección Civil, CERT/Ready.gov, and FAO/INTA/INIA-style agriculture manuals. A Spanish-first build like that is well under 10 GB before models, and still leaves room for a local chat model plus embeddings. 

For local chat over Spanish and bilingual content, the best balance in Ollama today is qwen3:8b as the main assistant and bge-m3 as the default embedding model. qwen3:8b is a 5.2 GB Q4 model, Apache 2.0 licensed, and explicitly supports 100+ languages and dialects. bge-m3 is a 1.2 GB multilingual embedding model with support for 100+ languages and an 8K context window. If you want a more compact multilingual embedder from the same ecosystem, qwen3-embedding:0.6b is 639 MB; if you want a lightweight multimodal fallback, gemma3:4b is 3.3 GB, supports 140+ languages, and provides a long 128K context window. 

The key design recommendation is therefore not “Spanish-only everywhere.” It is Spanish-first, bilingual where necessary: use Spanish ZIMs and official Spanish PDFs wherever a good equivalent exists, and reserve English only for the categories where Spanish coverage is still materially weaker. That gives the repo a clean --lang es path without sacrificing the “restart civilization” objective. 

Current repo structure and English payloads
The repo’s five profiles are layered. survival-essential pulls the basic survival and medical core plus general-knowledge-lite; survival-plus extends that with repair, agriculture, food, and travel; civilization-core adds foundational textbooks and a smaller public-domain library; civilization-rebuild adds engineering/making and extended textbook/public-domain layers; and civilization-max adds the large “maxi” Wikipedia tier on top of rebuild. 

Within those profiles, the English resources currently declared in the repo catalog include: survivalmanual-wiki, survivalmanual-ebook, simplewiki-zim, who-basic-emergency-care, wikem-zim, wikipedia-top1m-zim, wikipedia-medicine-zim, ifixit-zim, openstax-biology-2e, fao-small-agriculture-pack, wikivoyage-zim, gardening-stackexchange-zim, cooking-stackexchange-zim, wikibooks-zim, wiktionary-zim, appropedia-snapshot, energypedia-zim, open-source-ecology, cdc-public-health-pack, openstreetmap-wiki-zim, diy-stackexchange-zim, woodworking-stackexchange-zim, electronics-stackexchange-zim, arduino-stackexchange-zim, engineering-stackexchange-zim, 3dprinting-stackexchange-zim, bicycles-stackexchange-zim, wikisource-zim, libretexts-core-science, libretexts-physics, libretexts-chemistry, project-gutenberg-small, project-gutenberg-large, and wikipedia-top1m-maxi. 

The important implementation detail is that the source schema does not yet encode language or variant selection. That means Spanish support should be added in one of two ways: either as parallel source IDs such as wikipedia-es-top-zim, wikibooks-es-zim, ifixit-es-zim, and so on; or through a language-aware resolver that maps a neutral logical ID like wikipedia-top-zim to wikipedia_en_top_nopic_* or wikipedia_es_top_nopic_* depending on --lang. The first option is simplest to audit and lock; the second is cleaner for long-term maintenance.

Spanish equivalents and gap analysis
The best Spanish substitutions fall into three buckets. First are direct offline equivalents — especially Kiwix ZIMs — where you should swap English for Spanish one-for-one. Second are official Spanish PDF/manual packs, which are better than community translations for medicine, emergency response, and civil defense. Third are content-gap categories, where a good Spanish offline corpus does not cleanly exist, so the right answer is either a curated Spanish snapshot or an intentional English fallback in --lang both.

Highest-value Spanish resources to prioritize
The following Spanish resources are the best additions to the repo, in priority order, because they are either direct offline equivalents or unusually strong official Spanish corpora: wikipedia_es_top_nopic, wikipedia_es_medicine_nopic, ifixit_es_all, wiktionary_es_all_nopic, wikibooks_es_all_nopic, wikisource_es_all_nopic, wikivoyage_es_all_nopic, vikidia_es_all_nopic, WHO BEC Spanish page and flyer, WHO BEC Spanish quick cards, Cruz Roja emergency-kit checklist, Cruz Roja first-aid guidance, Ready.gov CERT participant manual in Spanish, Protección Civil flood-risk guide, Protección Civil operational-response guide, Protección Civil emergency communications guide, Appropedia Spanish pages, Energypedia Spanish category/pages, OSE Spanish wiki pages, Project Gutenberg Spanish browse/results, and the Biblioteca Virtual Miguel de Cervantes catalog and downloadable HTML/PDF texts. That gives you well over the requested twenty high-value Spanish resources across encyclopedia, travel, dictionary, medical, emergency, agriculture, repair, energy, maker, and literature domains. 

Manifest design for Spanish packs
The most maintainable approach is to create parallel Spanish source IDs and then define Spanish profiles such as core-50-es and civilization-lite-es. That aligns with the existing source/profile schema cleanly and avoids overloading the current schema with a partially-implemented language abstraction. 

The following snippets use direct URLs derived from the official Kiwix, WHO, Cruz Roja, Protección Civil, Ready.gov, Project Gutenberg, Cervantes, Appropedia, Energypedia, and OSE sources cited in this report. For community snapshots, the size is an engineering estimate for the packaged output, not an upstream published exact size.

Local retrieval and Ollama strategy
The indexing design should stay hybrid. Use Kiwix as the native browser/search layer for ZIMs, because it is already the right tool for Wikipedia-family content and avoids exploding disk usage by extracting everything. Then build a sidecar retrieval index only for: Spanish PDFs, small ZIMs you want to expose directly to chat, and curated HTML snapshots such as Appropedia ES, Energypedia ES, OSE ES, Gutenberg ES selections, and Cervantes selections. In practice, a good stack is: FTS5 for lexical recall, sqlite-vec for dense retrieval against chunk embeddings, and Kiwix for direct browsing/open-on-citation behavior. The important practical rule is to not pre-extract giant ZIMs unless you specifically need them in RAG; otherwise disk usage grows much faster than the source archive itself.

For Spanish content, the retrieval policy should be:

Search Spanish-first corpora first.
If the Spanish hit quality is thin and --lang both is enabled, fan out to English gap-fillers.
Prefer official PDFs/manuals over community wiki pages for medical or emergency topics.
Prefer repair/how-to corpora like iFixit ES over generic encyclopedic text for troubleshooting.
Keep a source-family weight in ranking: WHO/OPS/FAO/Protección Civil/Cruz Roja above community wiki pages, and curated topical ZIMs above giant general encyclopedias.

Checksum policy should be simple and strict: for official static files, record a local SHA-256 after download and lock it in the repo; for Kiwix ZIMs, lock both the exact filename and a local SHA-256; for curated snapshots, version them by crawl date + seed URL set + generated SHA-256. That gives you reproducibility even when the upstream site does not prominently publish a SHA-256.

Implementation notes and limitations
The top-level tools/ directory visible in the current repo snapshot contains utilities such as catalog-refresh.mjs, checksum-release.mjs, manifest-lint.mjs, source-audit.mjs, and zim-probe.mjs, but no obvious standalone public “installer” entrypoint is visible there. That means the right documentation change is to show --lang es as an extension to the manifest resolver, not as a promise tied to a specific script name that may not exist yet or may be implemented elsewhere in the app layer.

Sample resolver logic
python
Copy
def resolve_source(logical_id: str, lang: str) -> list[str]:
    mapping = {
        "simple-encyclopedia": {"en": "simplewiki-zim", "es": "vikidia-es"},
        "general-knowledge-top": {"en": "wikipedia-top1m-zim", "es": "wikipedia-es-top"},
        "repair-manuals": {"en": "ifixit-zim", "es": "ifixit-es"},
        "medical-quickref": {"en": "wikem-zim", "es": "who-bec-es"},  # intentional non-1:1 substitute
    }

    if lang == "both":
        hits = []
        if "es" in mapping.get(logical_id, {}):
            hits.append(mapping[logical_id]["es"])
        if "en" in mapping.get(logical_id, {}):
            hits.append(mapping[logical_id]["en"])
        return hits

    if lang in mapping.get(logical_id, {}):
        return [mapping[logical_id][lang]]

    return [mapping[logical_id]["en"]]

Open questions and limitations
A few areas remain intentionally conservative rather than over-claimed. I did not positively confirm a current, maintainable Spanish Project Gutenberg ZIM in the Kiwix mirrors I reviewed, so I recommend a curated Gutenberg ES mirror instead of promising a drop-in ZIM. I also did not find a like-for-like Spanish replacement for WikEM, the maker/engineering Stack Exchange layers, or the English LibreTexts/OpenStax-style STEM bundles. For those categories, the best repo design is explicitly bilingual rather than pretending Spanish parity exists today. Finally, community wiki sources such as Appropedia and Energypedia are extremely valuable, but they need page-level license verification during packaging, because the reviewed pages show open-license intent and mixed file-level tags rather than one single globally uniform packaging rule. 

The most robust final architecture, then, is:

--lang es for a clean Spanish-first offline pack.
--lang both for the full “survival + restart civilization” goal.
Kiwix ZIMs for large reference libraries.
Official Spanish PDFs for medicine and emergency response.
Curated HTML snapshots for Spanish community-tech and literature corpora.
qwen3:8b + bge-m3 as the default local chat stack.
