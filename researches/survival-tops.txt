System design: offline survival + civilization knowledge repo

The best architecture is not to put 50–200 GB of files directly into GitHub. The public GitHub repo should contain the blueprint, manifests, scripts, checksums, indexing tools, and app code. Users run one command and the repo downloads the selected packs from official sources into a local data/ folder.

The design should have two editions:

Core-50 Pack — under 50 GB, includes survival knowledge, core science, high-value Wikipedia subsets, offline search, and a local Ollama chat model.
Civilization-Rebuild Pack — larger optional edition, optimized for compressed storage, with broader science, agriculture, engineering, medicine, manufacturing, governance, repair, and reference materials.

The best overall stack is:

Kiwix ZIM files + Markdown/PDF manuals + SQLite FTS5 + sqlite-vec + Ollama + Qwen3 8B + BGE-M3 embeddings.

1. Key design decision

A strict “under 50 GB including LLM” build should not include the full English Wikipedia all_nopic file, because that file alone is about 48 GB, leaving no room for the LLM, indexes, manuals, or other scientific data. The better compact choice is to combine a broad Wikipedia subset with targeted science/medicine ZIMs. Kiwix currently lists wikipedia_en_all_nopic at about 48 GB, while wikipedia_en_top1m_nopic is about 16 GB and wikipedia_en_simple_all_maxi is about 3.2 GB.

So the best compact design is:

Use compressed ZIM files for broad reference knowledge, curated open manuals for practical survival/rebuild tasks, and a small local RAG index over the most practical documents.

Do not vector-index all of Wikipedia in the compact version. Let Kiwix handle Wikipedia search, and let the LLM RAG system index the curated manuals, textbooks, and extracted practical guides.

3. Best local Ollama model
Default model: qwen3:8b

Use:

ollama pull qwen3:8b
ollama pull bge-m3

Reason:

qwen3:8b is about 5.2 GB in Ollama’s Q4_K_M quantization.
It is Apache 2.0 licensed.
It is designed for reasoning, instruction following, multilingual use, and tool integration.
It is small enough for a normal 16 GB RAM PC, and often usable on 8 GB RAM machines with reduced performance.
Embedding model: bge-m3

Use bge-m3 for the RAG index.

Reason:

About 1.2 GB.
Supports up to 8192 tokens.
Designed for multilingual and multi-function retrieval use.
Better for long technical chunks than tiny embedding models.
Low-end fallback

For old or low-RAM machines:

ollama pull gemma3:4b
ollama pull nomic-embed-text

gemma3:4b is around 3.3 GB and has a long context window, while nomic-embed-text is only about 274 MB. This gives a smaller offline AI option when disk/RAM are limited.

Alternative model

llama3.1:8b is also a strong local option at around 4.9 GB and supports a 128K context window, but its license is less permissive than Qwen3’s Apache 2.0 license. I would include it as an optional model, not the default.

Include in Core-50
ligi/SurvivalManual

This should be included. It is a survival guide based on the public-domain US Army Survival Field Manual FM 3-05.70 and is designed to work offline.

Recommended handling:

git clone https://github.com/ligi/SurvivalManual.git data/repos/SurvivalManual
git clone https://github.com/ligi/SurvivalManual.wiki.git data/repos/SurvivalManual.wiki

Then convert wiki pages to Markdown/text chunks for search.

inferno986return/SurvivalManual-ebook

Include this too. It converts the SurvivalManual wiki into an ePub/PDF-style format. The project states that it copied the wiki using git clone and that the ePub is under 4.5 MB. It is useful because printable/e-reader formats matter when power is limited.

Recommended handling:

git clone https://github.com/inferno986return/SurvivalManual-ebook.git data/repos/SurvivalManual-ebook
Do not include as survival content
CreativeLyons/NukeSurvivalToolkit_Wiki

Despite the name, this is documentation for the Nuke Survival Toolkit, a Nuke compositing/software toolkit, not human survival. It is useful as an example of how to package an offline wiki as HTML/PDF, because it provides release ZIPs and an offline index.html workflow, but it should not be part of the survival knowledge pack.

Use it as a packaging reference only.

Use carefully
alx-xlx/awesome-survival

This repo is useful as a discovery index, but it should not be blindly mirrored. It links to many survival resources, but some are magnets, copyrighted collections, weapons-related items, or legally questionable sources. It should be used only to identify legitimate, open, civilian survival resources. The final project should avoid copyrighted dumps, offensive weapons material, and dangerous procedural content.

5. Best knowledge sources for Core-50
A. Wikipedia / Kiwix

Use Kiwix ZIM files as the main compressed knowledge format.

Why:

ZIM is compressed and designed for offline web archives.
Kiwix supports offline reading, local search, and serving content over a local network.

Kiwix is designed for offline access to web content and can serve content locally, making it ideal for this project.

6. Best storage formats

Use different formats for different layers.

Content type	Best format	Why
Wikipedia / Wikimedia	.zim	Highly compressed, searchable, offline-ready.
GitHub wikis	Markdown + HTML	Easy to read, diff, chunk, and index.
Manuals	PDF + extracted .txt / .md	PDF preserves original; text powers search/RAG.
Textbooks	PDF + extracted text	Human-readable and machine-searchable.
Metadata	SQLite	Portable, one file, reliable.
Full-text index	SQLite FTS5	Built-in full-text search, portable.
Vector index	sqlite-vec	Keeps vectors in the same SQLite ecosystem.
App config	YAML manifests	Easy to audit and edit.

SQLite FTS5 is a strong default because it is designed for efficient full-text search over large document collections and supports ranking, phrase search, prefix search, boolean queries, and highlighting.

For vectors, sqlite-vec is the best fit for this project because it is a small SQLite extension, written in C, designed to run anywhere SQLite runs, and supports vector search without needing a separate database server.

Avoid making Chroma, Elasticsearch, or OpenSearch the default. They are useful, but heavier. Chroma can be an optional developer backend because it is open-source and designed for embeddings and retrieval, but SQLite is simpler for offline survival use.

10. Offline search and chat flow
Search flow
User query
   ↓
Local web UI
   ↓
SQLite FTS5 search over manuals/textbooks
   ↓
Kiwix search over ZIM encyclopedia files
   ↓
Results shown with source path, title, category, license
AI chat flow
User question
   ↓
Query rewritten by app
   ↓
Hybrid retrieval:
   - SQLite FTS5 keyword search
   - sqlite-vec semantic search
   - optional Kiwix search
   ↓
Top source chunks selected
   ↓
Prompt sent to Ollama Qwen3 8B
   ↓
Answer generated with citations to local files

The LLM should not be treated as the source of truth. It should be a reasoning interface over local documents.

The prompt should force this behavior:

You are an offline survival and science assistant.
Answer only using the retrieved local sources.
Cite every factual claim with local source IDs.
If the archive does not contain enough information, say so.
Do not invent procedures.
Do not provide offensive weaponization, harmful biological, or illegal instructions.
Prefer safe, civilian, public-health-focused guidance.

The long version should be modular. Users should choose how much they want to download.

Long Pack philosophy

The long pack should prioritize:

Compressed source files first
Extracted text only where useful
Indexes only for curated high-value documents
Avoid duplicated content
Avoid huge raw scientific corpora unless curated

The full goal is not “download everything.” The goal is:

Store the smallest possible set of knowledge that preserves the ability to recover food, water, medicine, energy, materials, tools, science, education, and governance.
